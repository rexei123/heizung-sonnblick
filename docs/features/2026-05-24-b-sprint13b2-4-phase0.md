# B-Sprint13b2-4 Phase-0 — 409-Subtype-Diskriminator

**Stand:** 2026-05-24
**Zweck:** Audit-Befunde vor Implementierungs-Brief.
**Rolle:** Code (Read-Only-Audit, Autonomiestufe 3)
**Branch:** `docs/b-sprint13b2-4-phase0`
**Strategie-Setzung 2026-05-24 (verbindlich):**

- Diskriminator-Mechanismus: `error_code`-Feld im Response-Body.
- Codes pro Exception-Klasse, nicht pro Sub-Case:
  - `POOL_DEVICE_UNAVAILABLE`
  - `DEVICE_STATE_ERROR` (deckt alle `DeviceStateError`-Sub-Cases)
  - `SELF_REPLACEMENT_FORBIDDEN`
- Scope strikt auf Lifecycle-Endpoints.
- Aufwand-Ziel 2-3 h.

## 2. API-Endpoint-Exception-Handling

`backend/src/heizung/api/v1/devices.py`, drei Lifecycle-Endpoints:

### POST `/api/v1/devices/{id}/replace/from-pool` (Z.440-501)

Vier `except`-Branches in `replace_device_from_pool` Z.467-481:

```python
except DeviceNotFound as exc:
    raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail=str(exc)) from exc
except PoolDeviceUnavailable as exc:
    raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail=str(exc)) from exc
except DeviceStateError as exc:
    raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail=str(exc)) from exc
except ValueError as exc:  # Selbst-Tausch
    raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail=str(exc)) from exc
```

`HTTPException`-Build: `detail=str(exc)` — also Body ist heute `{detail: "<message-string>"}`. **Kein** `error_code`-Feld. Vier 409-Faelle, drei davon nicht unterscheidbar fuer den Caller ohne String-Parsing (PoolDeviceUnavailable / DeviceStateError / ValueError-Selbsttausch).

### POST `/api/v1/devices/{id}/retire` (Z.504-552)

Zwei `except`-Branches in `retire_device_endpoint` Z.524-534:

```python
except DeviceNotFound as exc:
    raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail=str(exc)) from exc
except DeviceStateError as exc:
    raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail=str(exc)) from exc
```

Analog: `detail=str(exc)`, kein `error_code`. Hier nur ein 409-Case (`DeviceStateError`) — Disambiguation gegen 4xx-Geschwister nicht noetig, aber Konsistenz zum Replace-Endpoint pflicht.

### GET `/api/v1/devices/pool` (Z.162-178)

Keine `try/except`-Bloecke. `get_pool_devices` liefert eine Liste (potenziell leer), kein 4xx-Pfad. **Nicht betroffen** vom Diskriminator-Pattern.

**Soll-Stand nach Implementierungs-Brief:** `HTTPException(... , detail={"detail": <message>, "error_code": <CODE>})` ODER `detail` bleibt String und ein zusaetzliches Top-Level-Feld `error_code` wird gesetzt — siehe Audit 4 zur Schema-Wahl.

## 4. Schema-Empfehlung

### Heutige Repo-Konvention (Inkonsistenz-Befund)

`git grep -n "error_code|exception_class" backend/src/heizung/api/` zeigt **eine** bestehende Verwendung mit zwei verschiedenen Patterns in derselben Datei `backend/src/heizung/api/v1/overrides.py`:

| Zeile | Pattern | Hinweis |
|---|---|---|
| 200-210 | `detail={"error_code": "room_override_blocked", "room_id": e.room_id}` | nested-detail-object **mit `error_code`-Key** (Sprint 12c, AE-58 RoomOverrideBlockedError) |
| 211-219 | `detail={"error": "room_not_occupied", "room_id": e.room_id}` | nested-detail-object **mit `error`-Key (nicht `error_code`!)** (Sprint 12a T3, AE-58 RoomNotOccupiedError) |

Beide nutzen das Pattern "detail-as-object" (nicht "detail-as-string + sibling error_code"). Aber: **inkonsistente Key-Namen** (`error_code` vs `error`). Pre-existing Repo-Drift, nicht von dieser Phase-0 ausgeloest.

### Strategie-Setzung 2026-05-24

Brief-Wortlaut: `{detail: "...", error_code: "POOL_DEVICE_UNAVAILABLE"}` — also **`detail` bleibt String, `error_code` als Top-Level-Sibling**. Das ist eine **dritte** Konvention, weicht von beiden bestehenden overrides.py-Varianten ab.

### Empfehlung Phase-0

Implementierungs-Brief sollte die Konvention klar fixieren. Drei Varianten zur Wahl:

| Variante | Body-Form | Pro | Con |
|---|---|---|---|
| (a) Strategie-Setzung 1:1 | `{detail: "<msg-string>", error_code: "<CODE>"}` | Strategie-Wortlaut erfuellt; `detail` bleibt rueckwaerts-kompatibel zu `str(exc)`-Konsumenten | Drittes Pattern im Repo zusaetzlich zu den zwei aus overrides.py — Konvention-Inkonsistenz waechst |
| (b) Nested wie overrides.py:200-210 | `{detail: {error_code: "<CODE>", message: "<msg>"}}` | Konsistent zu Sprint-12c-Pattern (juenger als 12a `error`-Pattern); ein klares Repo-Pattern | Brief-Wortlaut weicht ab; bricht Bestandstests die `detail`-as-string assumen (siehe Audit 5) |
| (c) (a) + Konsolidierung in eigenem Hygiene-Sprint | wie (a), zusaetzlich neuer Backlog-Item, overrides.py umstellen auf konsistente Form | Strategie 1:1 + Repo-Konvention spaeter heilbar | Hygiene-Sprint-Aufwand entkoppelt |

**Phase-0-Empfehlung: (c)** — Strategie-Wortlaut respektieren, Konsolidierungs-Backlog-Item parallel dokumentieren (Implementierungs-Brief erwaehnt das). Begruendung: (b) bricht heute mehr Tests (Audit 5) als (a), und Brief-Wortlaut ist klar.

### FastAPI-Implementierung

FastAPI `HTTPException(detail=...)` rendert `detail` direkt als JSON-Wert (kann String, Dict, Liste sein) — das Top-Level-Sibling-Pattern (a/c) braucht entweder einen **Custom-Exception-Handler** (App-weit via `@app.exception_handler(HTTPException)`) oder einen Wrapper-Helper, der bei Lifecycle-Endpoints aufgerufen wird. Implementierungs-Brief muss das festlegen.

## 7. Empfehlungen fuer Implementierungs-Brief

1. **Custom-Exception-Basisklasse anlegen:** `services/device_service.py` ergaenzt `class LifecycleError(Exception): code: ClassVar[str]` (oder analog). `DeviceNotFound`, `DeviceStateError`, `PoolDeviceUnavailable` erben davon, plus neue `SelfReplacementForbidden(LifecycleError)` ersetzt den inline-`ValueError` Z.126. Pro Klasse `code` als ClassVar definiert (z.B. `code = "POOL_DEVICE_UNAVAILABLE"`).
2. **API-Endpoint-Exception-Handler vereinheitlichen:** Statt 4 `except`-Branches pro Endpoint einen **App-weiten `@app.exception_handler(LifecycleError)`** registrieren, der `{detail: str(exc), error_code: exc.code}` rendert. Reduziert Boilerplate in `api/v1/devices.py` von 4+2 except-Branches auf 0 (oder 1 fallback fuer DeviceNotFound→404 Status-Code-Mapping, falls Basisklasse nicht selbst Status traegt).
3. **Frontend-Diskriminator-Schicht generisch anlegen:** Neue Datei `frontend/src/lib/api/error-codes.ts` mit `ErrorCode`-String-Enum (`POOL_DEVICE_UNAVAILABLE` / `DEVICE_STATE_ERROR` / `SELF_REPLACEMENT_FORBIDDEN` / `DEVICE_NOT_FOUND`). `ApiError`-Type in `types.ts` um optionales `error_code?: ErrorCode` erweitern. ReplaceDeviceDialog + RetireDeviceDialog auf `apiErr.error_code === ErrorCode.POOL_DEVICE_UNAVAILABLE` umstellen, die 5 Regex-Stellen + 2 Modul-Konstanten loeschen.
4. **Test-Erweiterung:** `test_api_devices_lifecycle.py` ergaenzt pro 409-Pfad eine `assert resp.json()["error_code"] == "<CODE>"`-Assertion. `sprint13b2-device-replacement.spec.ts` Case 3 Mock anpassen + ggf. neuer Case 6 fuer `SELF_REPLACEMENT_FORBIDDEN`-Pfad (falls Hotelier den ueber UI triggern kann — eigentlich blockiert durch Dropdown, also evtl. nur Backend-Test).
5. **Backlog-Item B-Sprint13b2-7 anlegen:** Konvention-Konsolidierung `overrides.py:206` (`error_code`) vs Z.214 (`error`) als eigenen Hygiene-Sprint. Implementierungs-Brief erwaehnt das, schliesst es aber explizit aus dem 13b2-4-Scope aus.

## 8. Offene Fragen fuer Strategie-Chat

1. **Schema-Variante (a) Top-Level-Sibling vs (b) Nested-detail-Object:** Strategie-Wortlaut sagt (a). Repo-Konvention in `overrides.py` ist (b)-Familie aber selbst inkonsistent (`error_code` vs `error`-Key). Bestaetigung dass (a) gewollt ist trotz Repo-Drift — oder Strategie-Korrektur auf (b) mit Test-Anpassung der zwei `assert "..." in detail`-Stellen in `test_api_devices_lifecycle.py`.
2. **`DEVICE_NOT_FOUND`-Code fuer 404er:** Strategie-Wortlaut hat nur 3 Codes (alle 409). 404er via `DeviceNotFound` koennen auch einen Code bekommen (`DEVICE_NOT_FOUND`) — konsistenter, aber 404er sind heute generisch genug behandelt. Strategie-Entscheidung: ja/nein.
3. **App-weiter Exception-Handler vs Per-Endpoint:** Empfehlung-Punkt 2 schlaegt App-weit vor, weil kuerzer. Strategie hat keinen expliziten Wunsch hinterlassen. Bei "nein": jeder Lifecycle-Endpoint behaelt die except-Bloecke, faengt aber jetzt mit `error_code`-Feld-Setzung. Mehr Boilerplate, lokaler.

Sonst keine offenen Fragen — Brief-Skizze ist klar genug fuer Implementierungs-Brief-Erstellung.
